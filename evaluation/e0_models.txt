# Candidate models for the EmoNet-Face E0 sweep.
# Columns: <hf_id> <lf_template> <weights_gb> <act_gb_per_sample> <env> <notes>
#
# weights_gb        resting VRAM after the model loads (VramTracker's after_load).
# act_gb_per_sample activation + KV cost per image in a batch, at --max-image-pixels 262144.
#
# Both are MEASURED. Peak VRAM is linear in batch size -- evaluation/vram_profile.py's sweeps
# show it cleanly (Qwen2.5-VL-3B activations at bs 4/8/16: 2.00 / 4.08 / 8.21 GB) -- so these
# two numbers reproduce every measured point and extrapolate to any card:
#
#     peak_gb(bs, arm) = weights_gb + act_gb_per_sample * bs * ARM_FACTOR[arm]
#
# evaluation/vram_map.py inverts that for the largest batch a given GPU pool can hold and
# emits the matching gres request. It replaces the old `shard_gb` and `batch_size` columns,
# which were measured once on a 46 GB A40 and then reused verbatim -- on the HPC cluster's 80 GB A100
# that left more than half the card idle, and on the `ours` arm GLM-4.6V-Flash used 22.6 GB
# of a 35 GB request.
#
#     python evaluation/vram_map.py --gpu a100 --arm paper_retry
#     python evaluation/vram_map.py --gpu a40  --arm ours
#
# Where the slope came from: (peak - weights) / batch_size on each model's completed
# `paper_retry` run -- the FULL runs, not the profile sweeps. The profiles ran `paper_once`
# over 16 images and understate a real run, because it is generated length, not prompt
# length, that drives the KV cache. Fitting the profile and then applying a blanket safety
# factor punished models that were already cheap: gemma-4-12B's real arm cost is 1.04x, so a
# global 1.5x pushed it from a batch of 8 that demonstrably worked down to 6. Fitting the
# most expensive arm directly makes the table reproduce every measured peak by construction,
# and vram_map.py's ARM_FACTOR scales the cheaper arms down from there.
#
# MiniCPM-V-4.6's two numbers are back-solved from an old 28 GB shard request, not measured,
# and they are WRONG IN BOTH DIRECTIONS. Measured 2026-08-18: resting VRAM after load is
# 3.1 GB, not 18.00 -- so the sizing is wildly conservative -- yet the `paper_once` arm still
# OOM'd at bs=28 (job 41427, one 41.82 GiB allocation on a 44.42 GiB card). The reason is that
# `act_gb_per_sample` is a single number per model while the arms differ enormously in prompt
# length: the benchmark's phrasing plus a 151k-vocab fp32 logit tensor dominates, and the
# `ours` arm at bs=24 fits fine (job 41426, 2385/2500 parsed in 53 min). Until this row is
# profiled per arm, run paper_once with BATCH_OVERRIDE=8.
#
# The reason it went unmeasured for two weeks is NOT that it failed: it passed its smoke on
# 2026-08-04 at 17:03, and collect_smoke.sh wrote the survivor list at 17:14 gating on a
# result file that landed at 17:15. See the note in that script.
#
# Measured at --max-image-pixels 262144, which beat 1048576 on every single model while using
# 5-7 GB less VRAM. A larger pixel cap raises the slope (GLM 0.78 -> ~1.15), so these numbers
# are valid at 262144 only -- re-profile if that changes.
#
# The shard request itself has not changed meaning: the A40 nodes advertise shard:a40:144
# over 3 GPUs (48 shards per 46 GB card, 960 MiB each) and the H100 node 94 shards per card
# (1019 MiB), so a shard is ~1 GB on both and sizes port across pools. Requesting gpu:a40:1
# reserves no VRAM at all and lets two models collide on one card, which is how
# Ministral-3-14B OOM'd with 15 MiB free. the HPC cluster has no shard gres and allocates whole GPUs.
#
# WARNING on batch sizes above 16: vram_profile.py defaulted to --images 16 and builds one
# batch from exactly that many images, so bs=24 silently re-ran the same 16 as a batch of 16
# and reported identical numbers. This file's previous claim that "throughput saturates at
# batch 16 (24 measures identically), so 16 is the cap" was that artifact, not a finding.
# VRAM above 16 extrapolates cleanly; THROUGHPUT above 16 has never been measured. Re-profile
# with --images 128 --batch-sizes 8,16,32,64 before treating the top of the range as a
# throughput recommendation.
#
